# 论文容量管理

配置在项目 `config.toml` 的 `[capacity]`：候选上限 200，精选上限 100，规则版本 `retention-v1`。容量不是配额，不为填满降低资格、全文或总结审校门槛。每日候选 50、完整交付 3 和原每日 12:00 任务保持原样。

## 操作

在项目 PowerShell 中使用原入口；它进入既有 WSL Python，与每日任务共用运行锁：

```powershell
.\run.ps1 capacity status
.\run.ps1 capacity preview
.\run.ps1 capacity apply
.\run.ps1 capacity restore --paper-id 实际稳定ID
.\run.ps1 capacity pin --paper-id 实际稳定ID
.\run.ps1 capacity unpin --paper-id 实际稳定ID
```

`status` 和 `preview` 只读；在系统临时目录读取数据库及 WAL 的稳定副本，不向 Vault、生产数据库或状态文件写入。遇到并发数据库变化请重试。预览包含每篇稳定 ID、实际排序依据、排序向量、保留门槛、拟迁移目的地和异常。`apply` 在同一运行锁内重新计算并执行，不盲目执行可能已过时的预览。无超额、无符合重新评估条件的归档时不移动论文。

归档目录按需生成：`80_归档/候选归档`、`80_归档/论文归档`。正式论文移动整个文件夹；候选主笔记移动后，其共享或项目数据区附件仍留原位置并修复引用。所有原始 PDF、双语 PDF、证据与审校附件、手写区、缓存和已完成处理阶段保留。不会为整理重新下载、总结或翻译。

## 排序依据

这是阅读区保留顺序，不是对论文科学质量的量化评价。采用确定的字典序，前项优先于后项：

1. 用户明确固定保留。
2. 既有 `search.keywords` 在题名或摘要中有匹配的优先；没有匹配属于相关性未明确；`search.exclude` 命中的为当前方向不优先。匹配数量不累加质量分。
3. 用户明确标注 `capacity_reading_value: high` 且提供非空 `capacity_reading_reason` 的阅读价值优先。没有标注表示未指定，不意味着质量差；不把 AI 自动总结里的赞美语转成分数。
4. 当前正式资格门槛已通过的优先；其次比较已保存的发表核验来源、状态与核验记录是否齐备。仍由原 `classify` 和白名单判资格，固定和容量不能代替资格。
5. 当前已完成且有据可查的处理阶段及资源字段的数量：pdf、fulltext、daily_summary、auto_review、translation、delivery；PDF/译文阶段还要求本地文件存在。资源只计已有元数据的 HTTPS code_url/data_url/project_url。此项是资料准备程度，不是论文质量、实测复现成功或代码可用性认证；缺失仍为未知。原记录没保存资源字段时不从自然语言猜测。
6. 已保存发表／预印本／论文集年份的时效性，仅按年比较，不把抓取时间当发表时间，不补造月份或日期。如果当前比较集合里任意一篇年份未知，则整组不用年份打破平局。
7. 同分优先保留当前已在对应区域的论文；最后按稳定 paper_id 升序，确保结果确定。新论文的入区前集合先持久化，中断重跑仍保留这一平局规则。

精选的新交付继续走原全文、总结、原文审校、双语交付流程；新增入口检查 `gate.eligible`。恢复已归档精选还要求**当前正式资格通过且原完整交付仍通过 `completed` 检查**，不靠移动目录制造合格论文。

每次执行保存 `data/production/capacity/decision-*.json`，逐篇列出保留、归档或恢复原因、证据、排序向量、门槛、版本和操作前后数量。归档后的未变化记录不再无条件参与竞争；仅主题／发表资格证据、内容版本、资料准备状态、用户阅读偏好或固定字段实质变化时重新评估。抓取时间、核验时间本身变化不会触发。指定 `restore` 也只是重新竞争，未胜出会继续归档；固定不能越过精选资格门槛。

## 固定和手写保护

可用上述 pin/unpin 命令，也可在论文 YAML 中填写布尔值：

```yaml
capacity_pin: true
capacity_reading_value: high
capacity_reading_reason: 与我的当前课题直接相关，准备复现实验
```

只有 `capacity_pin: true` 代表固定；字符串 `"true"` 会报告格式冲突。固定计入容量，不被自动归档。固定数量超限、恢复导致固定数量超限时暂停该区域自动迁移并报告，不取消固定。手写区标题、系统占位文字、实际手写内容均不用于推断固定；实际手写内容始终保留。固定归档记录会触发重新评估，仍须遵守资格和容量。

## 一致性、恢复和异常

实际候选笔记生成、正式发布、旧流程 process、期刊补标都接入容量检查，并复用原运行锁；日常失败候选写入后也检查容量。统一路径函数识别归档位置，已归档 delivery/pdf/fulltext/translation 阶段不清空；每日扫描跳过未变化的归档记录。

迁移前创建 `capacity/operation-*/`，包含 SQLite 一致性备份、要移动的全部资产副本、所有将改写 Markdown 的原字节和回执；先写 `capacity/pending.json` 再移动。移动后核验附件哈希，只修复 Markdown/Wiki 引用和数据库中的路径值，保留历史交付数量、时间、内容版本和用量。原始模型响应、缓存和历史原始回执不改写；路径沿革可从迁移回执查证。完整保留/归档/恢复决定另有 decision 回执。

普通异常自动回滚；进程中断则在下一次容量执行、候选写入、发布或补标前恢复未完成迁移。恢复前核验文件是否仍是原字节或本次计划生成的字节，发现中断后外部修改则暂停，保留文件和备份，不能覆盖用户新编辑。没有后台无限重试。可以运行 `capacity apply` 触发恢复并重新整理。

重复 ID、未知 ID、非法固定字段、缺少身份的主笔记或归档索引不一致，均报告并保守暂停受影响区域的自动迁移，其他区域仍可处理。目标冲突不会覆盖。Obsidian 或其他应用不参与项目锁；请勿在实际移动的短时间内并发手工移动文件。此实现使用当前真实生产 WSL 调用链；不要从另一个操作系统同时绕开该入口运行维护脚本。

当前 active、archived、pinned 是按稳定 ID 去重的目录现状；historical_delivered 是数据库成功交付过的累计稳定 ID 数，不因归档减少。查看状态时会并列显示。历史每日简报保留原事实，仅迁移必需时修链接；整理不重生成日报。
